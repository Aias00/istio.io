[Mixer](/zh/docs/reference/config/policy-and-telemetry/) はリクエストパスに現れるため、自然に疑問が生じます：それはシステムの可用性と遅延にどのような影響を与えるでしょうか？Istio のアーキテクチャ図を初めて見たとき、人々が最もよく尋ねる質問は："これは単一障害点の典型的な例ではないですか？"

この記事では、Mixer の設計原則を深く掘り下げ、それらの原則のもとで Mixer がメッシュ内のシステムの可用性を驚くほど向上させ、平均リクエスト遅延を削減できることを説明します。

Istio の Mixer は、システム全体の可用性と遅延に対して 2 つの主な利点があります：

* **SLO の向上**：Mixer はプロキシとサービスをインフラストラクチャのバックエンドの障害から隔離し、高度で効率的なメッシュ可用性保障を提供します。全体として、同インフラストラクチャのバックエンドとの相互作用では、Mixer の支援のおかげで、より低い障害率が得ら

* **遅延の削減**：Mixer は、さまざまなレベルのキャッシュを積極的に使用および共有することで、平均遅延を削減します。

上記の内容について説明します。

## Istio はどのように生まれたのか{#how-we-got-here}

Google は、Google が提供する多数の API を処理するために、内部の API とサービス管理システムを長年使用しています。このシステムは、最大規模のサービス群（Google Maps、YouTube、Gmail など）をサポートし、数百万 QPS のピークを処理します。このシステムは確かに良く動作しますが、Google の急速な成長にはまだ追いつけず、明らかに、運用コストの飛躍的な上昇を抑えるために新しいアーキテクチャが必要です。

2014 年、私たちはこのシステムを置き換えるための草案を開始し、より良いスケーラビリティを実現するために準備しました。この決定は最終的に非常に正しかったことが証明されました。Google 全体での導入後、月あたり数百万ドルの運用コストが削減されました。

## アーキテクチャの概要{#architecture-recap}

下図では、Mixer はメッシュとインフラストラクチャの間にあります：

{{< image width="75%" link="./mixer-spof-myth-2.svg" caption="Istio 拓扑" >}}

論理的には、Envoy Sidecar は、リクエストの前に Mixer を呼び出し、プレチェックを行い、リクエストの後に指標レポートを行います。Sidecar にはローカルキャッシュが含まれており、ほとんどのプレチェックはキャッシュを使用して実行できます。また、Sidecar は送信する指標データをバッファリングするため、Mixer を数回呼び出すことができます。プレチェックとリクエスト処理は同期的であり、指標データの送信は非同期で fire-and-forget モードで実行されます。

抽象一点说，Mixer 提供：

* **バックエンド抽象**：Mixer は Istio コンポーネントとメッシュ内のサービスをインフラストラクチャの詳細から隔離します。

* **中間者**：Mixer は運用者がメッシュとインフラストラクチャのバックエンド間の相互作用を制御できるようにします。

これらの純粋な機能に加えて、Mixer には他の特徴もあり、システムにより多くの利点を提供します。

### Mixer：SLO 向上器{#mixer-booster}

Mixer は SPOF であり、メッシュのクラッシュを引き起こすと言われていますが、私たちは Mixer がメッシュの可用性を向上させると考えています。これはどのように実現されるのでしょうか？以下は 3 つの理由です：

* **ステートレス**：Mixer はステートレスであり、独自の永続ストレージを管理しません。

* **安定**：Mixer は高い信頼性を持つコンポーネントであり、すべての Mixer インスタンスが 99.999% 以上の信頼性を持つように設計されています。

* **キャッシュとバッファリング**：Mixer は大量の短期状態データを蓄積できます。

Sidecar プロキシは各サービスインスタンスとともに実行され、メモリを節約する必要があるため、ローカルキャッシュとバッファリングの数を制限します。しかし、Mixer は独立して実行されるため、より大きなキャッシュとバッファリングを使用できます。したがって、Mixer は Sidecar に高いスケーラビリティと高い可用性を持つ 2 次キャッシュサービスを提供します。

Mixer の予想される可用性は、多数のバックエンド（多くの場合 99.9%）よりもはるかに高いです。そのローカルキャッシュとバッファリングは、バックエンドが応答しない場合でも実行を継続できるため、インフラストラクチャの障害からの遮蔽に役立ち、影響を軽減します。

### Mixer：遅延削減器{#mixer-latency-slasher}

上記で説明したように、Istio Sidecar は効果的な 1 次キャッシュを備えており、トラフィックを提供する際に多くの時間でキャッシュを使用して完了できます。Mixer は 2 次キャッシュとしてより大きな共有プールを提供し、これは Mixer の平均リクエスト遅延を削減するのにも役立ちます。

遅延を削減するだけでなく、Mixer はメッシュからバックエンドへのリクエスト数を削減するため、インフラストラクチャのバックエンドの QPS を大幅に削減できます。これらのバックエンドに支払いを行う場合、この利点はより多くのコストを節約します。

## 今後の課題{#work-ahead}

私たちは、システムに対してさらに多くの改善を行う機会があります。

### 金絲雀デプロイメント方式での設定の発行{#configuration-canaries}

Mixer は高いスケーラビリティを備えており、通常は故障しません。しかし、誤った設定がデプロイされた場合、Mixer プロセスがクラッシュする可能性があります。このような状況を防止するために、金絲雀デプロイメント方式で設定を発行できます。まず、小規模な Mixer をデプロイし、その後、デプロイ範囲を拡大します。

現在の Mixer はこの機能を備えていませんが、私たちはこの機能が Istio の信頼性の高い設定作業の一部として最終的に発行されることを期待しています。

### キャッシュの調整{#cache-tuning}

Sidecar と Mixer のキャッシュはさらに調整が必要です。この部分の作業は、リソース消費の削減とパフォーマンスの向上に焦点を当てます。

### キャッシュの共有{#cache-sharing}

現在の Mixer のインスタンスは独立しています。1 つのリクエストが特定の Mixer インスタンスによって処理された後、その過程で生成されたキャッシュは他の Mixer インスタンスに渡されません。私たちは最終的に Memcached や Redis などの分散キャッシュを試験的に使用し、メッシュ範囲の共有キャッシュを提供し、バックエンドのインフラストラクチャの呼び出し頻度をさらに削減することを期待しています。

### シャーディング{#Sharding}

大規模なメッシュでは、Mixer の負荷が重くなる可能性があります。私たちは大量の Mixer インスタンスを使用し、各インスタンスが各自のトラフィックを維持することができます。私たちは、特定のデータフローに対して特定のサービスを提供するように Mixer インスタンスを調整するスマートシャーディング機能を導入することを希望しています。言い換えれば、シャーディングは、類似のトラフィックを同じ Mixer インスタンスに割り当てることで、キャッシュ効率を向上させることができます。つまり、ランダムに選択された Mixer インスタンスにリクエストを渡すのではなく、リクエストを特定の Mixer インスタンスに割り当てることで、

Google の実際の経験は、軽量プロキシと大規模キャッシュコントロールプレーンの結合の利点を示しています：より良い可用性と遅延を提供します。過去の経験は、より正確で効果的なキャッシュ、プレチェック、バッファリング戦略などの機能を構築するのに役立ちました。また、キャッシュがヒットしない場合のパフォーマンスへの影響を軽減するために、通信プロトコルを最適化しました。

Mixer はまだ若いです。Istio 0.3 では、Mixer に重要なパフォーマンス改善はありません。つまり、リクエストが Sidecar キャッシュにヒットしない場合、Mixer はより多くの時間を費やします。今後数か月間で、同期プレチェックプロセス中のこの状況を最適化するために多くの作業を行います。

私たちは、読者が Mixer が Istio に与える利点を理解できることを望んでいます。
