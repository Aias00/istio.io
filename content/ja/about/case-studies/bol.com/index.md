Bol.com は、書籍から電子製品、園芸用品まで、すべての商品を販売するオンライン小売業者です。
この会社は 1999 年に設立され、現在、1100 万人以上の顧客にサービスを提供しています。
その技術スタックと IT インフラストラクチャは、これまで大幅に成長してきました。

彼らの商業運営の背後にあるインフラストラクチャは、以前はサードパーティーによってホストされていましたが、
bol.com は最終的に独自のインフラストラクチャを構築し、自動化することを決定しました。
2010 年末、bol.com はクラウドに移行しました。
クラウドに移行するサービスが増えるにつれて、チームは、クラウドベースのサービスとインフラストラクチャを構築およびデプロイする権限を与えられます。

## 課題 {#challenge}

当 bol.com 开始将业务迁移到云端时，彼らは成長の陣痛を避けることができませんでした。
彼らは、アプリケーションを Kubernetes クラスターに移行し、時間の経過とともに Pod を増やしました。
最初のクラスターのアドレス空間には、十分な空間があるように見えました。
残念ながら、需要の急速な拡大は、すぐに問題になりました。
彼らは最初にクラスターにサービス CIDR を設定し、その中に約 1000 個のアドレスの空間を設けましたが、
1 年後には、その使用量が 80% に達しました。

Roland Kool は、bol.com チームのシステムエンジニアの 1 人で、この問題を解決しました。
Kubernetes クラスター内の使用可能な IP アドレス空間が、急速に成長するビジネス要件を満たせないという問題に直面しました。
チームは、溢出する IP アドレスを他のクラスターに入れるためのソリューションが必要でした。
さらに、この新しい多クラスター Kubernetes デプロイは、サービス検出、負荷分散、およびセキュアな通信を行う新しい方法をアプリケーションが必要とするという新しいネットワークの課題をもたらします。

## ソリューション：サービスメッシュを使用したマルチクラスター {#solution-multiple-clusters-with-a-service-mesh}

ソリューションは、追加のクラスターを導入するように見えますが、セキュリティ要件とサービス間のトラフィックを保護するネットワークポリシーの問題に直面しました。

個人識別情報（PII）を保護する必要性は、この課題をさらに悪化させました。
GDPR などの欧州法規により、PII を含むすべてのサービスは、アクセスを厳密に制御する必要があります。

ネットワークポリシーはクラスター固有のものであるため、クラスター間で動作することはできません。
したがって、各クラスターのネットワークポリシーはすぐに混乱しました。
チームは、より高いレベルでセキュリティを適用するソリューションが必要でした。

Istio の[マルチクラスターデプロイメントモデル](/zh/docs/ops/deployment/deployment-models/#multiple-clusters)は、最終的に完璧なソリューションとなりました。
[認可ポリシー](/zh/docs/reference/config/security/authorization-policy/)を使用すると、異なるクラスター間のワークロードが安全に通信できます。
Istio を使用すると、Kool のチームは、OSI 第 3 層または第 4 層ネットワークポリシーから、第 7 層で実施される [authz ポリシー](/zh/docs/tasks/security/authorization/authz-http/)に移行できました。
Istio の強力な ID サポート、サービス間の認証、および相互 TLS（mTLS）のセキュリティにより、この移行が可能になりました。

これらの変更により、bol.com は、新しい Kubernetes クラスターを追加して、新しいビジネス要件を拡大すると同時に、
サービス検出と負荷分散に必要なセキュリティポリシーを維持できます。

## なぜ Istio なのか？ {#Why-Istio?}

bol.com が最初に Kubernetes に移行したとき、Istio のバージョンは 0.2 でした。
それはまだ本番環境に備えていないように見えたため、Istio なしで進むことにしました。
Istio の調査を本格的に始めたのは、1.0 バージョン付近でしたが、
デプロイと実装に関する問題が多すぎたため、このアイデアは放棄されました。

しかし、拡張の問題だけではなく、bol.com が Istio ソリューションを再採用する理由は、新しい監規制要件でした。
これらの要件は、様々なサードパーティーサービスと API と安全に通信する必要があります。
これらの制御は、変化するファイアウォールルールと IP 範囲に基づくことはできません。
これらは、アプリケーションの ID に基づく必要があります。

彼らのソリューションは、[Istio 出口ゲートウェイ](/zh/docs/tasks/traffic-management/egress/egress-gateway/)を利用しています。
これにより、クライアントワークロードの ID または名前空間、ターゲットホスト名、

bol.com は、マルチクラスター展開をサポートするサービスメッシュが必要で、Istio がまさにその要件を満たしています。
さらに、Istio は特定のニーズを満たすために必要な細かい制御を提供します。

## 結果：DevOps の有効化 {#results-enabling-devOps}

“Istio のデプロイは簡単です。”Roland Kool は、“あなたがインストールすると、すぐに実行されます。”

Istio をインストールした後、彼らは、彼らにとって重要なサービスメッシュの機能を実装することに着手しました。
Sidecar の導入には、各チームの追加の作業と、Istio の実装を担当するチームのサポートが必要です。

Kool と bol.com チームの最大の変化の 1 つは、突然、サービス実装の認可ポリシーが容易になったことです。
現在、bol.com での Istio の使用率は約 95% で、まだ成長しています。
すべての開発者が満足することは困難かもしれませんが、Istio デプロイメントチームは、容易に導入して統合するように努力しています。

開発者は、Istio の多くの機能を熱心に受け入れ、良いフィードバックを提供しました。
彼らは、アプリケーションがクラスター間で相互通信するのがいかに簡単かを見て、嬉しく思いました。
Istio のおかげで、すべての接続が簡単に設定および管理できます。

bol.com のインフラストラクチャは、継続的に発展しています。
Istio が提供する可
[Istio と Prometheus の統合](/zh/docs/ops/integrations/prometheus/)により、
必要なメトリクスと診断情報を収集して、ロードマップがどこに導くべきかを理解できるようになりました。
今後の計画には、ロードバランシングサービスの統合、新しいテスト方法、分散トレーシング、
および会社のより多くのインフラストラクチャへの Istio のインストールが含まれています。
