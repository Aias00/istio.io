英国 Auto Trader は 1977 年に設立され、英国の主要な自動車市場雑誌です。
20 世紀末、オンラインビジネスに転換したとき、それは英国の第 16 位のウェブサイトに発展しました。

AutoTrader をサポートする IT 領域は非常に広範囲です。現在、Auto Trader は
40 から 50 個の顧客向けアプリケーションを管理しており、それらは約 400 個のマイクロサービスによってサポートされています。
1 秒あたり 30,000 以上のリクエストを処理します。彼らの公開基盤は Google Kubernetes Engine（GKE）上で実行されており、
Istio サービスメッシュを利用しています。主要な Istio 成功事例の 1 つとして、Auto Trader は 2018 年に公有クラウドサービスへの移行が注目されています。
その移行の背景と継続的な利益を理解する価値があります。

## 課題 {#challenge}

内部およびサプライヤーの要件の変化により、Auto Trader は GKE と Istio に移行しました。
特に、すべてのマイクロサービスに対して相互 TLS（mTLS）を透過的にデプロイする必要がありました。
このような努力は、主要なカスタム基盤にとっては不可能でした。

パートナーとサプライヤーの要件により、mTLS のデプロイは必須でした。
Auto Trader は、ほとんどの基盤を公有クラウドに移行する計画を立てています。
強力なエンドツーエンド mTLS は、そのマイクロサービス環境を保護するために不可欠です。

## ソリューション：Istio と Google Kubernetes Engine {#solution-Istio-and-Google-Kubernetes-Engine}

Auto Trader の IT チームは、サービスを公有クラウドに移行することに関して優れた記録を持っています。
明らかに、これはより多くの基盤の最終的な目的地です。mTLS の実装に関する問題に直面したとき、
IT チームの一部は、Istio をサービスメッシュとして使用して、既存のアプリケーションをコンテナ化し、GKE にデプロイすることを試みました。

実験は成功しました。GKE 上で数日で、他のチームがプライベートクラウドで数週間かかった作業を完了しました。
さらに、Istio サービスメッシュは、マイクロサービス環境全体で、エンドツーエンドの mTLS を提供します。

{{< quote caption="Karl Stoney，Auto Trader 基础设施交付领导" >}}
私たちは、Istio を試してみて、どうなるかを見てみることにしました。最終的に、私たちは約 1 週間で、過去 4 ヶ月間自分でそれを実装するよりも多くの時間を費やしました。
{{< /quote >}}

## なぜ Istio を選択したのですか？{#why-Istio}

すべてのマイクロサービスが mTLS への移行が容易であるという点は、Istio を選択する上で非常に強力な理由です。
Istio は、多くの大規模な組織でサポートされています。
Auto Trader は Google と提携しているため、Google が Istio の強力なサポーターであることを知っていることで、それがサポートされて長期的に発展することを確信しています。

GKE 上で Istio を使用した実験が早期に成功したため、すぐに
その機能を数ヶ月間実装しようとしていたものが、短い期間で準備が整いました。
Istio は、mTLS だけでなく、信頼性の高いリトライとバックアップ戦略、および異常検出も提供します。

## 結果：現象可観測性 {#results-phenomenal-observability}

Istio により、Auto Trader は、すべてのアプリケーションを公有クラウドにデプロイすることに自信を持つことができました。
可観測性が向上するにつれて、彼らは、基盤を管理および考慮する新しい方法を持つようになりました。
彼らは突然、パフォーマンスとセキュリティに関する洞察を得るようになりました。
同時に、Istio は、長年存在していた未発見の欠陥を発見するのに役立っています。

### プラットフォームデリバリーチームの誕生 {#emergence-of-a-platform-delivery-team}

彼らは、Kubernetes と Istio のソリューションを内部製品として、他の開発者とデプロイメントチームに提供することができます。
10 人のチームが現在、200 人以上の他の開発者にサービスを提供するデリバリープラットフォームを管理しています。

Kubernetes の最初の意図は、より良いアプリケーションのデプロイとリソース管理を実現することでした。
しかし、Istio を追加することで、アプリケーションのパフォーマンスに関する深い洞察が得られるという利点があります。
可観測性は重要です。
Auto Trader は、正確なリソース利用とマイクロサービストランザクションを測定できるようになりました。

これは完全に透過的な移行ではありませんが、Istio と Kubernetes の利点は、すべての製品チームを移行することを奨励しました。
Istio は、管理する依存関係が少なく、多くの機能を自動的に提供できるため、プロジェクトチームは、ほぼ手を加えずに、機能間の要件を満たすことができます。
チームは、数分でグローバルに Web アプリケーションをデプロイできるようになりました。
新しい基盤は、約 200 から 250 のデプロイメントを毎日処理できます。

### CI/CD の有効化 {#enabling-CI-CD}

新しいアプリケーションであれば、5 分でデプロイできます。
既存のアプリケーションの迅速なデプロイは、Auto Trader のリリース方法を変えました。
彼らはリリースサイクルを使用するのではなく、CI/CD を使用して新しい変更を迅速にデプロイします。
使用 Istio
での微調整の監視により、デプロイメントチームは、新しいデプロイメントの問題を迅速かつ正確に特定できます。
各チームは、自分のパフォーマンスダッシュボードを確認できます。
新しいエラーが見つかった場合、CI/CD ダッシュボードを使用して、すぐに変更をロールバックできます。
Istio の復旧時間は数分です。

Auto Trader は、大規模で完全にカスタマイズされた IT 資産を購入し、それらをシステム的にマイクロサービスに移行しました。
Istio の実装は、移行の成功の重要な部分であり、全体的な組織により良いプロセス、より良い可観測性、およびより良いアプリケーションを提供します。
